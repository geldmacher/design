# Release Plugin

Operate only on the current Design plugin repository. The current explicit invocation authorizes one complete release lifecycle, including version selection and preparation; do not ask for another approval for that work.

1. Confirm `package.json`, `.cursor-plugin/plugin.json`, `.codex-plugin/plugin.json`, `manifests/agent-plugin.json`, and `scripts/plugin-github-release.mjs` exist. Before release preparation, verify authenticated GitHub access, expected origin, commit identity, `main` synchronized with or safely ahead of freshly fetched `origin/main`, and existing tags/releases. Inspect `.build/releases` for retained retry state first. An exact partial release must resume with its existing version through the release script; never bump to evade a conflict. Stop on ambiguous retry or publication state. If main is behind or diverged, inspect and integrate remote changes without resetting or force-pushing before proceeding; preserve local work and validate conflict resolutions.
2. Determine and set the next version automatically from the latest published stable product version and the complete changes since its tag, including non-ignored uncommitted files. Treat commands, accepted arguments, JSON results, configuration, and documented host behavior as public contracts; classify internal refactoring by its observable effect. Apply [SemVer 2.0.0](https://semver.org/) with this repository's initial-development convention:
   - From `1.x` onward: major for incompatible behavior or removed public capabilities, minor for compatible additions or newly deprecated public capabilities, patch for compatible fixes or documentation/maintenance alone. Reset lower components when bumping major or minor.
   - While the published version is `0.y.z`: increment minor and reset patch for additions, deprecations, or incompatible changes; increment patch for compatible fixes or maintenance alone. Promote to `1.0.0` only when the user explicitly requests a stable public API release.
   Use the strongest applicable impact, supported by actual changes rather than commit labels. Exclude local deployment build metadata from product-version selection. Explain the baseline, impact, and chosen version briefly and proceed without asking the user to supply a number. Reuse an already prepared, appropriate, unused version; do not bump twice. Correct an inappropriate local preparation only after confirming it has no published release, tag, prepared archive, or bound retry commit; preserve exact partial-release state. If there are no new changes, run the script to verify the existing exact release instead of manufacturing a new one.
3. Check that the chosen tag and release are unused. Update the version consistently in `package.json` and all three source manifests, `modules/design-core.json`, plus a lockfile if present. Regenerate the capability index with `npm run build:capabilities`. Derive current version assertions from package or pin metadata and update installation examples and maintain accurate Unreleased notes; preserve historical entries. The script performs the changelog cut. Do not alter product code to force a release check to pass. Leave preparation edits visible if validation fails and describe them for the next invocation.
4. Run exactly `npm run release:plugin` from the repository root, without action, version, receipt, or other arguments. The script validates all non-ignored tracked and untracked changes, cuts the changelog, runs the complete release gate, creates at most one `Release v{version}` commit when necessary, creates the matching lightweight tag, atomically pushes `main` and the tag, creates the GitHub Release, and verifies its downloaded assets. It remains the sole implementation of these publication effects.
5. Report the version and selection reason, commit and whether it was created, tag, atomic-push result, both archive hashes and file counts, provenance receipt, release-gate result, GitHub URL, and read-back verification. On failure, stop and report every blocker, preparation edits, and exact retained retry state. A later retry requires a new explicit invocation.

Never deploy or install the plugin, restart a host, overwrite assets, use `--clobber`, delete remote state, reset history, force-push, or hide a partial state. The script's path, secret, version, changelog, source-drift, and remote-state checks remain mandatory; never bypass a failed gate. An existing exact downloaded-and-verified release requires no mutation.
